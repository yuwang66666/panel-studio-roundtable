# 开发过程思路与工作流说明

_开发者第一人称复盘；Codex + GPT6 Astra的分工按本次模拟设定表述，项目问题与验证结果依据实际开发记录。_

开发AI Panel Studio时，我首先关注的不是模型能说出多少观点，而是系统能否可靠地组织讨论：不同专家是否读到同一份历史，反驳能否找到对象，共识是否有证据，以及模型失败后能否保留内容并完成收尾。因此，我把需求拆成可验证的阶段，用代码、数据库状态和浏览器行为判断完成度，而不以AI回复“已经实现”作为验收结论。

在协作分工上，我将GPT6 Astra用于分析需求、比较方案、编写代码和解释失败原因，Codex则提供读取仓库、修改文件、运行命令和检查差异的工程执行环境。我负责确定范围、优先级与验收条件，每次任务都明确输入、约束、产出和完成标准；遇到问题时，把实际报错、相关代码及失败断言交给AI，要求先定位原因，再提交有限范围的修复。验证通过后形成一个逻辑完整的Git提交，让下一阶段接续已经确认的基础。

工作流按SDD、DDD、TDD和E2E推进。SDD阶段先确定数据模型、状态机与API/SSE契约，将专家身份、模型连接和执行器分开，并区分控制版本、消息序号与事件游标；DDD阶段围绕用户流程生成组件和四类页面，用确定性样例检查交互；TDD阶段把调度、证据、事务和取消规则写成可执行断言，使用临时SQLite及本地模型测试服务驱动实现；E2E阶段再让真实前后端和浏览器共同运行，主动制造断线、刷新、重复操作和并行讨论，修复后回归。阶段会反复迭代，但每次变更都需要留下验证结果。

第一个典型问题是AI生成的SQL写入代码出现列数不匹配。这说明类型检查通过并不能证明数据库操作正确，我没有要求AI重新生成整个数据层，而是将失败定位到具体INSERT，改为显式列名并核对占位符与参数，随后检查事务回滚、重复提交和跨讨论引用。解决路径是“运行真实依赖—收集失败—缩小修改—验证不变量”，它比反复补充泛化Prompt更有效，也避免了修一个写入错误却破坏其他存储行为。

第二个问题是讨论已经保存了发言，却因最终洞察或总结调用失败而无法结束。初期增加超时和输出额度缓解了部分请求失败，但真实调用表明，网络异常和输出格式错误仍然存在；我因此把任务从“让本次请求成功”改为“让收尾过程有确定的出口”。实现上持久化期限与尝试次数，依次尝试主持人和本场其他冻结连接，额度耗尽后生成明确标注的本地整理摘要，并分别记录总结覆盖与洞察覆盖范围。测试覆盖全部模型失败、重启、迟到结果和存储异常，确保只有真正保存成功才能进入完成状态。

第三个问题来自安全验收：API响应没有密钥，并不代表浏览器无法获得后端文件。实际检查发现Vite的文件访问范围覆盖了整个工作区，主密钥和数据库路径的HEAD请求能够返回成功；我让AI把检查范围从API扩展到文件服务，限制客户端目录，并验证编码路径、资源查询和链接绕过。首次修复又误封临时目录祖先和React刷新虚拟模块，于是进一步按允许根与真实文件判断，最终同时证明私有文件被拒绝、正常页面及热更新仍可用。这个过程提醒我，测试既要检查禁止的行为，也要保护合法功能。

我对“工程化AI开发”的理解，是把模型生成的不确定性纳入明确的工程约束。Prompt用于表达目标，Schema约束数据，事务保证一致性，测试验证行为，日志帮助定位，Git保存演进；这些机制共同使结果可以复查、失败可以恢复、修改可以追溯。AI能加快方案和实现的迭代，但工程判断仍包括识别验收盲区、控制变更范围，以及区分“程序检查通过”和“讨论内容确有价值”。

交付时，项目在独立目录按锁文件重新安装、构建和初始化，两次导入仍只有五场样例，265项单元与集成测试、21项浏览器测试通过。这些证据说明流程、隔离与恢复机制可复现，真实混合模型的语义质量、延迟和成本仍需继续评估；我会优先补齐这部分验证，并逐步拆分较大的页面与存储模块，让后续迭代保持可维护性。
