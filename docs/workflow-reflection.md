# 开发反思

本次开发从空目录开始，采用“契约—页面—测试—业务实现—浏览器联调”的顺序。用户明确要求每完成一部分都验证，因此阶段完成依据是实际命令结果与可观察行为。T00首先验证Node、pnpm、SQLite驱动和前后端启动。这里立即暴露了Windows环境中未激活的Node入口、安装缓存权限以及子进程找错pnpm的问题。如果只生成工程文件而不启动，这些问题会留到交付时才出现。

数据设计中最有价值的决定是分开角色、模型连接与讨论执行器。专家身份随话题生成，模型连接独立保存并可复用。启动时冻结配置版本，使后续编辑不会改变在途请求的模型。密钥只存在于后端凭据层，公开连接类型使用严格白名单。与此同时，将频繁变化的事件序号和控制命令版本分开，避免一条新发言就让用户的结束命令失效。

动态讨论的难点集中在时序和边界。每轮专家从同一快照判断参与，仲裁器再选择发言者，只让被选中的专家生成完整短句。等待公平性、连续发言限制和有效回应优先通过确定性测试验证。模型输出本身仍可能重复，因此补充了重复关注点和持续分歧的主持人介入条件。单场状态更新保持可串行解释，跨场模型调用受统一并发控制。全员pass、部分模型失败、提前结束和预算不足均需要明确出口，不能依赖模型自行停止。

共识提炼需要两层校验。程序能够证明消息ID真实存在、归属当前讨论、支持者数量足够，以及最后一条发言已被处理；它不能单凭这些条件证明模型准确理解了语义。实现因此保留证据跳转，并将局部共识与全体共识明确区分。总结必须在最终洞察覆盖完成后提交，失败时保留已有内容。真实供应商尚未配置，人工语义检查被如实列为后续验收项。

实时机制采用数据库事件日志作为事实来源。消息与事件同事务提交，快照返回对应游标，SSE从数据库补发。浏览器去重并在发现序号缺口时重新同步。端到端测试实际断网、恢复并刷新，确认18条消息完整且不重复；向上阅读时，新发言入口出现而页面位置保持。一次浏览器用例通过后，测试进程却因Windows子进程清理挂起，说明验收还必须包含测试本身能正常退出。最终将隔离的Vite和API放到同一测试进程管理，问题才完整解决。

AI辅助开发加快了组件与重复契约的编写，但首轮生成仍出现SQL占位符数量、条件表达式括号、模块模式和可访问名称匹配等具体错误。有效做法是把错误转成可复现检查，修复后重跑对应验收，再进入下一阶段。现阶段自动测试说明流程、隔离与恢复机制可复现；真实模型的讨论价值、延迟和费用需要实际连接数据。下一轮工作的优先级是补齐真实多供应商验收，并依据观察到的失败模式改进Prompt与调度，而不是提前增加更多功能。
