# 核心开发 Prompt：多范式阶段记录

本文包含10段可直接用于引导AI开发的工程Prompt，根据项目的真实代码、阶段提交及验收结果重新编写。它们是**开发过程的整理重构稿，不是当时逐字留存的原始会话**；未用用户需求原话充当工程Prompt，旧版需求摘录仍可在Git历史中查询。

SDD指规格驱动开发，DDD在本文指设计驱动开发（Design-Driven Development），TDD指以可执行测试驱动实现与修正，E2E指系统级端到端验证。范式标签说明工作方法，实际提交顺序和验证结果以[Git演进](git-history.md)及[阶段验收](verification.md)为准；不把现在编写的Prompt或修正建议声称为当时逐字发送过的指令。

## P01 · 【SDD阶段】数据建模与API契约生成

```text
先为圆桌系统建立可执行规格，再让前后端依赖这份规格实现功能。

将模型连接、连接版本、讨论、参与者、角色绑定、正式发言、洞察、证据、公开事件和命令回执分别建模。参与者保存本场身份，模型连接保存可复用的调用配置；启动讨论时冻结连接版本，不能让后续配置修改影响已开始的会话。

在packages/contracts中定义严格Zod Schema及TypeScript类型，列明REST方法、路径、请求体、响应、错误码与SSE事件。公开摘要只能包含凭据是否已配置，API Key、内部参与意愿和供应商推理字段不得进入公开类型。

分别定义控制命令version、正式消息messageSeq、公开事件eventSeq与执行generation，不得混用。为消息、角色和洞察证据建立同场约束，明确重复命令、旧版本和跨场引用如何拒绝；创建、绑定、开始、结束、重试必须有清晰的状态前置条件。

交付Markdown PRD、Mermaid ER图和状态机、API/SSE文档、共享Schema及SQLite迁移。先用非法状态跳转和额外私有字段证明契约能拒绝错误输入，再通过类型检查；有歧义的字段应在此阶段解决，不能交给页面自行猜测。
```

**说明：** 意图是让数据、接口和状态机形成同一套可执行约束，解决专家身份与模型配置耦合、跨场引用等问题。关键修正是把生命周期版本与高频事件序号拆开，避免新发言不断使结束命令的版本失效。

**依据：** 提交 `2de7405`、`a01401a`；[共享契约](../packages/contracts/src/index.ts)、[数据模型](data-model.md)、验收T01/T04。

## P02 · 【DDD阶段】从讨论流程生成前端组件与页面

```text
依据已确定的公开契约实现一个可操作的中文演播厅原型，覆盖首页、模型设置、阵容确认和讨论现场。

先构建按钮、角色头像、模型选择、状态提示、发言卡和洞察卡等可复用界面单元，再组合页面。首页提供讨论入口；阵容展示姓名、职业、立场、专业标签和稳定颜色；现场同时呈现专家、发言及有证据的共识与分歧。发言只展示公开正文，回应链接应能定位原文。

用确定性数据贯通创建话题、查看阵容、选择模型、确认进入、阅读讨论和查看总结。原型路径清晰标识为演示，不发送真实模型请求。为加载、空列表、失败和不可执行操作提供可理解的反馈，不把所有状态简化成一张成功页面。

采用深灰背景、中文系统字体和16px正文基线，桌面按专家/现场/洞察分栏，窄屏用页签切换。为输入、按钮及页签提供明确的可访问名称，支持Tab和Escape；先在375、768、1024、1440px检查内容、焦点和证据定位，再接入正式API。

输出组件与页面代码，以及能走完原型流程的Playwright用例和截图。发现定位失败时核对真实可访问名称和DOM，不以延长等待时间掩盖交互错误。
```

**说明：** 意图是先把完整用户路径做成可验证的界面，再开展后端联调。初版连接表单曾因可访问名称夹带说明文字而使测试定位失败，修正方向是显式命名并复测；该密钥输入界面后来随环境配置方案移除。

**依据：** 提交 `49a4ebf`；[页面](../apps/web/src/App.tsx)、[按钮组件](../apps/web/src/components/ui/button.tsx)、[原型测试](../tests/e2e/prototype.spec.ts)、验收T02。

## P03 · 【TDD阶段】建立模型与持久化测试基线

```text
在继续实现业务前，建立无需真实API Key的确定性测试环境，并用它约束网关和Repository的行为。

实现一个本地HTTP模型测试服务，覆盖Chat Completions、Responses和Anthropic Messages。按阵容、意愿、发言、洞察、总结等用途生成符合Schema的固定输出，允许注入限流和非法响应；测试必须能检查请求协议及调用次数，而不是只返回永远成功的对象。

为每个集成场景创建独立临时SQLite目录，结束后关闭服务和数据库。编写事务回滚、同一turn重复提交、重复命令重放、跨讨论角色引用、连接版本冻结与凭据公开边界的断言，再实现对应存储路径。

使用真实SQLite和本地HTTP完成这些测试，不用全面mock替代被测边界。事务中只执行短时数据操作，模型请求不能占着事务等待；SQL写入显式列出字段，字段变化必须同时核对占位符和参数。

每次失败先定位是哪一个行为契约被破坏，修复后重跑相关用例，再运行现有测试和类型检查。交付测试服务、临时库机制、Repository测试和通过后的实现，保留实际失败与修复记录。
```

**说明：** 意图是让协议、事务和隔离问题能够稳定复现，不依赖供应商响应或账户余额。实际遇到SQL INSERT列数不匹配，修正为显式列名并通过事务、幂等和归属检查后才继续业务开发。

**依据：** 提交 `0ef736c`、`a01401a`；[模型测试桩](../tests/fixtures/provider.ts)、[测试环境](../tests/fixtures/harness.ts)、[Repository测试](../tests/repository.test.ts)、验收T03/T04。

## P04 · 【TDD阶段】用场景断言驱动自主发言调度

```text
实现由参与意愿驱动的讨论执行器，不能用专家数组下标循环安排发言。先把仲裁器做成纯函数，以相同输入得到相同结果，再接入异步模型调用。

测试至少包含：全员pass、有效反驳与补充竞争、连续三轮申请未获选、存在其他候选时连续发言限制、平局、过期快照、跨场或不存在的回应目标。每轮所有专家使用相同throughMessageSeq，只有获选专家生成正式发言，其他专家及时回到空闲状态。

按已约定的优先级仲裁，并以稳定规则解决平局；等待者提升不能绕过有效性检查。全员放弃时由主持人引导，连续两次无有效参与后进入收尾，不得不断消耗调用预算。

上下文保留最近12条完整发言，并补入合法回应目标及洞察所需证据；不能混入未来消息。专家输出限制为1–2句及总长度上限，允许一次修复，失败后不提交；验证中文标点、小数和常见缩写，不能只按句号字符粗暴计数。

用记录输入的模型桩验证同轮历史边界和实际调用次数。完成纯函数与执行器测试后再运行一个完整讨论场景，证明顺序由候选变化决定、无候选时能够停止。
```

**说明：** 意图是把“自主互动”落实为可检验的调度规则，同时避免公平性和异步返回顺序相互干扰。实际验证采用同轮快照及调用次数断言，并补入窗口外回应目标、过期意愿过滤和无人参与收束条件。

**依据：** 提交 `477c564`、`b2dab1c`；[上下文与短句校验](../packages/domain/src/context.ts)、[仲裁器](../packages/domain/src/scheduler.ts)、[执行器测试](../tests/engine.test.ts)、验收T07/T08。

## P05 · 【TDD阶段】证据约束下的实时洞察与初版总结

```text
为讨论加入运行中的洞察提炼，先写证据有效性断言，再把提炼接入正式发言提交后的触发机制。

每新增三条专家发言或出现明确反驳时触发提炼，同场任务串行，重复触发合并处理。洞察必须区分局部共识、全体共识、分歧和未解问题，引用本场已提交且不晚于本次快照的消息。

编写反例验证：跨讨论证据、不存在的消息、用总结当证据、重复支持者、只有一人支持却标为共识、没有全部专家支持却标为全体共识。检查失败时不得提交部分洞察；沉默不能作为支持证据。

本阶段的初版收尾策略要求最终洞察覆盖最后一条讨论发言，随后由主持人生成总结；总结失败时保留全部已存内容，重试不能重复专家发言或追加两条总结。消息、洞察和公开事件必须在各自事务成功后再推送。

使用本地HTTP模型服务验证运行状态下已经出现洞察，而不是只检查最终页面有一张卡片。交付证据校验函数、洞察服务、失败重试测试，并在界面提供可追溯的发言引用。
```

**说明：** 意图是防止模型把泛泛的观点描述当成已获支持的共识，挑战是同时约束证据归属、支持人数与覆盖范围。此处保留T09当时的严格收尾策略，后来发现最终洞察失败会阻塞总结，因此在P07对应的T20阶段修订为分开记录两种覆盖范围。

**依据：** 提交 `d144d33`；[证据校验](../packages/domain/src/insights.ts)、[洞察测试](../tests/insights.test.ts)、验收T09。

## P06 · 【E2E阶段】真实前后端流程、重连与系统隔离

```text
将页面、Fastify、SQLite和SSE放在同一个端到端场景验证；模型端使用可控本地服务，浏览器使用真实Edge，不通过拦截全部业务API伪造流程成功。

在隔离数据库和独立端口准备三种协议的测试连接，通过界面创建话题、确认阵容、分配模型并启动讨论。等待正式发言、运行中的洞察和最终总结，检查角色与模型对应正确，消息ID和turnId不重复。

讨论中主动断开浏览器网络，恢复后验证快照游标与事件补发；再刷新页面，确认既有发言完整。上翻阅读旧消息时产生新发言，断言容器位置保持并出现更新入口，点击后才能回到底部。

在集成层并行执行两场不同话题，逐项核对角色、上下文、消息、洞察和事件归属；双击开始或重放命令不得启动第二个执行器。补充手机页签、证据跳转、Escape关闭对话框和Tab焦点检查。

失败时保留截图和错误，修复后重跑受影响场景及完整回归。测试结束必须关闭HTTP、SSE、Vite和数据库，进程退出码为0才算完成；若Windows子进程清理挂起，改用可控的进程内服务生命周期。
```

**说明：** 意图是证明前后端与事件恢复机制真正协同工作，避免单元测试全部通过但用户刷新后仍丢消息。实际遇到ESM入口、下拉框定位及Windows测试清理挂起，修正模块声明与定位方式，并在测试进程内统一管理Vite/API后完成闭环。

**依据：** 提交 `a6c56d4`、`e26c1b6`、`225b114`；[正式浏览器测试](../tests/e2e/live.spec.ts)、[隔离测试](../tests/isolation.test.ts)、[事件测试](../tests/events.test.ts)、验收T10–T12。

## P07 · 【TDD阶段】从单次超时修复升级为可靠收尾

```text
已有讨论在最终洞察或总结调用失败后无法完成，单纯增加超时不能解决所有模型不可用的问题。为所有讨论实现有界收尾流程，并先覆盖故障场景再调整业务代码。

把收尾任务持久化，保存绝对期限、已用尝试数、冻结候选连接和最终洞察是否已尝试。总结优先使用本场主持人，失败后按稳定顺序尝试本场其他冻结连接，重复连接去重，鉴权或配置被拒绝的连接不反复尝试。

默认总期限六分钟、最多四次总结模型请求，修复也占尝试次数；最终洞察最多追加一次。耗尽期限、预算或候选后，根据已保存发言和已有核验洞察生成明确标注来源的本地整理摘要，保留原文引用，不虚构新的共识。

分开保存总结覆盖序号与洞察实际覆盖序号，允许最终洞察失败时仍对全部正式发言收尾。测试鉴权失败、超时、非法JSON、全部模型失败、预算耗尽、重启、重复请求、双场隔离、迟到结果和数据库异常；存储失败不得被转换成completed。

请求发出前原子记录尝试次数，重启后保留原期限和已用次数；总结正文、来源和完成状态同事务提交。交付迁移、状态恢复、模型回退、本地摘要及对应测试，以一次可靠保存的总结作为完成条件。
```

**说明：** 意图是把收尾可用性建立在明确预算和持久状态上，解决最终洞察或任何一个模型故障阻断交付的问题。真实收尾曾在模型连续失败及总期限到达后保存本地摘要，因此验收记录区分“可靠交付了内容”和“模型总结调用成功”。

**依据：** 提交 `6a0b477`；[收尾机制](summary-reliability.md)、[容错测试](../tests/summary-resilience.test.ts)、[收尾存储测试](../tests/closing-repository.test.ts)、验收T20。

## P08 · 【TDD阶段】公开状态、自然语言与隐藏字段隔离

```text
为专家状态和流式正文建立端到端公开边界，先用带独立标记的测试输入证明哪些字段允许进入快照、SSE和页面。

状态依据真实任务变化：判断意愿、等待并发或等待首段时为preparing，第一段非空公开正文到达后才为speaking，放弃、未获选、提交、失败和取消后回idle。草稿和对应状态同事务保存，旧generation及迟到turn不能改写当前状态。

公开关注点只用已保存的专业标签、正式发言范围和合法回应目标构造。内部proposedFocus、reasoning、thinking及未知嵌套字段不得投影给浏览器；不要把模型隐藏推理改名为公开摘要。

总结content不能只验证为字符串：它可能是JSON对象的序列化结果。实现有界的自然语言提取，只剥离明确允许的单字段包装；未知结构进入既有修复/回退路径，不拼接任意字段。流式未闭合结构先暂缓，最终完整输出仍需校验，Repository提交时再次守住边界。

覆盖三协议的普通响应与SSE、空白首段、修复清空、刷新重连、历史坏格式和无来源元数据的旧总结。旧记录在显示层安全整理时明确说明来源，不改写数据库原文；测试同时断言合法正文仍可展示，不能用隐藏整个区域来通过检查。
```

**说明：** 意图是让状态准确反映实际执行，同时把隐藏推理和结构化原文挡在公开数据与页面之外。实际发现内部关注点可能被直接展示、总结字符串仍可嵌入JSON，修正为公开信息构造、白名单正文提取及网关/存储/显示多处校验，并修正了旧测试中以探针响应冒充总结正文的测试桩。

**依据：** 提交 `d5ae2a2`、`a1492c5`；[状态测试](../tests/participant-state.test.ts)、[公开关注点](../packages/domain/src/participant-focus.ts)、[总结正文测试](../tests/summary-prose-integration.test.ts)、验收T22/T23。

## P09 · 【DDD阶段】【E2E阶段】响应式与文件边界质量闭环

```text
技术审查已发现开发服务器暴露私有文件、非演播厅页面依赖整页滚动，以及平板页签和超宽正文比例不合理。逐项修复，并为每个缺口提供能复现旧问题的验收。

从固定视口和剩余高度分配开始重构：首页概览与讨论列表、设置模型列表与偏好区、阵容标题/列表/操作区分别滚动。1100px及以下仅展示选中页签面板，补齐ARIA对应、左右方向键和Home/End；超宽屏扩大侧栏但设置上限，正文卡片最大56rem。

测试不能只断言body禁止滚动：准备26场讨论、20个模型、6位专家的长内容，检查每个容器确实溢出且能滚至末项，其他区域位置不变，底部按钮实际可见可点击。覆盖375、768、1024、1440、2560px及375×568短视口，并检查减少动态效果。
```
